- **How:** both builds are driven the same way: full hive, the zoom (revision 3: the close-up), then **one real mouse press** on cell 17 (the middle of the 7 x 5 frame, all neighbours Capped). `Engine.time_scale = 0.05` so the 0.18 s pop lasts 3.6 s real time; frames are captured when a clock node (its `_process` delta, scaled like the tween) reaches each T.
- **What is compared** (raw pixels cannot match: revision 3 is flat and top-down at camera size 15, 0.1 is upright at the isometric angle at size 6.7):
  1. **Projected size:** the on-screen width of the scraped cell's hexagonal face (its two flat sides, projected through each build's own camera) divided by its width at the settled end (T = 0.30 s). Tolerance 0.02. **Worst difference 0.0003** (at T = 0.015 s).
  2. **Rendered pixels:** the visible bright-yellow area of that cell in the captured frame (flood fill from the cell centre, R > 230, G > 230, B < 130) as a linear size, normalised at T = 0.165 s (from 0.18 s the 0.1 cell has left its slot and a flying copy replaces it). Tolerance 0.12 (the cell is partly hidden by raised neighbours, differently in the two views, so this is a sanity check). **Worst 0.0165** (at T = 0.090 s).
  3. The cell's `Mesh` scale against the formula 1.3 -> 1 over 0.18 s with TRANS_BACK / EASE_OUT: worst difference 0.0025 in both builds; first sample (T = 0.007 s) 1.246 of settled width, undershoot at T = 0.12 s (0.973) in both.

### Capped colour: diagnosis (owner: the spec, then Bob's lighting or the designer)

Cause, shown by experiment rather than guessed: the upright pose points the cell face along d = (0.7071, 0, 0.7071); revision 3's face pointed up. `Sun` is unchanged (basis row `(0.433, 0.5, 0.75)` toward the light). N.L is **0.837 upright against 0.5 flat**, so the same material is lit brighter. In a scratch script (no file changed) I rotated the Sun so that N.L equals 0.5 for the upright face; the capped pixel became **(229, 177, 46)**, revision 3's value. So the code and the materials are right (`cell_capped.tres` is albedo (0.85, 0.68, 0.18), roughness 1.0 as specified); the spec asks for an upright frame, an unchanged Sun and +-2 at once, and these cannot all hold. The Clarifications forbid widening the tolerance, so I report it. Capped vs uncapped still differ clearly (G 198 vs 255, 57 apart). **Proposed one-line fix, designer's choice:** either accept (255, 198, 52) as the new reference for the upright frame (update the spec's number), or Bob lowers the cell materials' response (for example a darker `cell_capped` albedo) so it reads (229, 177, 45) under the unchanged Sun.

### The headless `mesh_get_surface_count` errors (task 5): Godot 4.2.1's dummy renderer, not a prop scene or `.tres`

- A bare script with no game code: one `MeshInstance3D` (Box, Sphere or Cylinder mesh; 1 or 5 of them; 2 or 3 kinds) prints exactly **1**; one `Label3D` prints 1; a `MultiMeshInstance3D` 0; no mesh 0. The error appears when meshes are freed (teardown), once per free event, not once per mesh. The main scene freed after a frame prints 4 (`cycle` run: 4 before each free of a `main.tscn`).
- So 246 lines in a full `run_tests.gd` run (one set of 4 per freed `main.tscn`, 61 instances) is the same engine behaviour that revision 3 reported as 24 (its tests instanced scripts with `.new()`), only multiplied by the test count. Owner: Godot 4.2.1 headless. Harmless: the windowed runs print none, and the export is clean.
- Why revision 3's `main.tscn` was quiet: its meshes were built by script at run time and never freed inside the run; I did not need to chase that further.
