## The three questions

### 1. `t_real_touch_taps_crank`: a harness issue, not a game bug

The test sent `InputEventScreenTouch` with `Input.parse_input_event`. **Headless, `Input.parse_input_event` dispatches nothing at all, mouse events included.** Evidence (`broken-copy-runs/touchdiag.gd.txt`: 5 presses 0.21 s apart on a live `Centrifuge`, `turns_counted` read back):

| Run | via `Input.parse_input_event` + `flush_buffered_events` | via `root.push_input` |
|---|---|---|
| headless, touch | 0 of 5 | 5 of 5 |
| headless, mouse button | 0 of 5 | (the three `t_real_mouse_*` tests use `push_input` and pass) |
| windowed, touch | 5 of 5 | 5 of 5 |
| windowed, mouse button | 5 of 5 | n/a |

So Patricia's diagnosis is right, and the cause is the headless dummy display server, not the game: the handler counts a `ScreenTouch` (`centrifuge.gd` line 172) and works windowed. Fix (mine): the headless test now sends the touch with `root.push_input`. The Input-singleton path, where the engine's touch-to-mouse emulation also runs, is covered windowed by the new `touch_windowed.gd`: 6 touch taps spaced past the cap count exactly 6 turns, a 2.00 s touch hold counts 11 turns (1 + 2 x 5), release stops the counting. The emulated mouse twin does not double-count.

### 2. The `mesh_get_surface_count` errors: the engine (headless dummy renderer), not a game script

24 lines of `ERROR: Parameter "m" is null. at: mesh_get_surface_count (servers/rendering/dummy/storage/mesh_storage.h:110)` per `run_tests.gd` run (`run_tests_output.txt`).

- A bare 4-line `-s` script with one `MeshInstance3D` holding a `CylinderMesh` (no game script, no material) prints exactly 1 of them, at teardown.
- With a `printerr("@@ ", test)` marker before each test (a copy in the scratchpad): 1 error in each of 22 tests that build a `Centrifuge` or `Honeycomb` with `.new()`, 2 in `t_back_keeps_frame` (it also builds the close-up), none in the other tests.
- `main.tscn` and `harvest.tscn` instanced in a `-s` script for 300 frames, and `--headless --quit-after 300` on the real game: **0** errors. I did not find why the scene route is quiet.
- Owner: nobody in this repo; it is Godot 4.2.1 headless. It is harmless to the tests and absent from the "Done when" command. It does not occur windowed (`play_loop_output.txt` has none). I left stderr visible rather than hide it.

### 3. `play_loop.gd`: first run 22 failures, all one harness bug (mine), now clean

First run: the real hold never finished the frame (22.6 s, 4 of 10 jars) and everything after it failed. Cause: the test pushed the hold's button events with `root.push_input`, which does not update `Input`'s button state, and `centrifuge.gd` `_process` ends a mouse hold when `Input.is_mouse_button_pressed(MOUSE_BUTTON_LEFT)` is false (line 260). A real mouse sets that state, so this is not a game bug. Fix (mine): the two holds use a new `_mouse_button_os()` that sends through `Input.parse_input_event` (what the OS does; it also runs touch emulation). Clicks, drags and taps stay on `push_input`. After the fix: 1015 checks, 0 failed.
