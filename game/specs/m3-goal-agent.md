# M3: Goal-oriented coding agent (Assignment 5)

**The assignment** (MILESTONES.md, M3): a goal-oriented coding agent that "reads the GDD and the specs, scans `game/`, lists the missing features, scores them (value, dependencies, cost), picks an order, and runs the build process of `game/CONTEXT.md` (steps, contract check, parallel start, visual checks, snapshot tests, checkpoint commits) with fresh agent contexts, its reasoning on a blackboard."

**The course's wording** (pasted by the designer, 2026-11-06): "build a goal-oriented coding agent that reads a Game Design Document (GDD), scans your existing codebase, and automatically generates missing features. [...] your primary objective is to build and understand the reasoning layer—how the agent decides what to build and in what order." To build: **the priority scoring logic** (`priority_score()`), **the gap-detection pass** (scanned files against the required features), **the code-writing step**, and **the iteration loop** (re-scan after each write, stop when all requirements are met). Deliverables: (1) the agent's source code, (2) at least one working feature in the capstone game generated by the agent ("It must run"), (3) a README: what feature the agent built, why it selected that feature, and what manual changes were needed before accepting the code. Due 2026-11-15, 11:59 ET; 10 points.

**Shape:** one script, `_tools/goal_agent.py`, holds the reasoning layer as plain, testable code: scan, gaps, `priority_score()` and the loop. Only the code-writing step calls agents (Patricia, Bob and Quinn, on their usual models). There is no planner agent: the scoring the assignment grades lives in `priority_score()`, where it can be read and tested (designer asked for a model choice; see "Answered"). Rule from `game/CONTEXT.md` Process 8: scripts before tokens.

## What gets built

1. **Gap detection, `scan()` and `gaps()` in `goal_agent.py` (no tokens): what's missing.**
   - Reads the approved specs in `game/specs/`. Each numbered Change and each Quinn contract line becomes a goal.
   - For each goal, it checks the game for evidence that it's done: config keys in `scripts/default_config.tres`, node names in the scenes (as `contract_check.py` finds them), test names registered in `tests/run_tests.gd`, and the last `godot_run.py` summary.
   - Writes `game/reports/goal/<run>/gaps.json`. Each goal gets a status of done, partial or missing, plus the evidence for it.
   - Its fixtures cover one done, one partial and one missing goal, tested like `test_generate.py`.

2. **`priority_score(goal, gaps)` in `goal_agent.py` (no tokens): what to build first.**
   - A weighted sum, every weight in one table at the top of the file. The factors:
     - **unblocks**: how many other missing goals depend on this one (node contract, config keys, then scripts, then tests);
     - **value**: the player-facing play-test fixes rank above polish;
     - **cost**: estimated from the owner's average in `agent-runs.csv` and lower is better;
     - **ready**: zero if any dependency is still missing.
   - The loop builds the highest score next. Each score is written to the blackboard with its factors, so "why this one" can be read straight off it, as the README needs.
   - Unit tests pin the order on a fixture gap list (the handoff before scenes, scenes before their tests).
   - An ambiguous goal is not scored. It stops the run with the question (Process 1).

3. **The code-writing step and the iteration loop in `goal_agent.py`.**
   Until `gaps()` comes back empty (or a stop), it re-scans, scores, takes the top goal, and for it:
   - creates or reuses the worktree and branch;
   - briefs Patricia's handoff (Process 5), then Patricia and Bob in parallel, and Quinn from the spec. Each runs as a fresh headless `claude -p` with only its spec slice, as `generate.py` does;
   - runs `contract_check.py`, then the style loop or `ui_shots.py` for visual checks, then `godot_run.py`, the snapshot suite and `mutate.py --since`;
   - sends failures to the folder's owner (Process 9) with at most 2 fix rounds before it stops for the designer;
   - makes a checkpoint commit on the milestone branch when the step is green (designer, 2026-11-06: "why not?"). Never on `main`, never a push;
   - re-scans and loops. It stops when every goal of the spec is done, when the budget guard blocks, or after 2 failed fix rounds on one goal.
   Every call is logged by the run log hooks. `budget_guard.py` is honoured, and a blocked agent pauses the loop, never skips it.

4. **The blackboard: `game/reports/goal/<run>/blackboard.md`.**
   - It records the goal, the gap list, scores and order, each step's briefs (by reference), results and fix rounds, and the designer stops.
   - It is the A5 write-up's evidence, like `STYLE_LOOP.md` for A6.

5. **Demo run.** The agent builds **0.1.4** (`game/specs/0.1.4-ui-placement.md`) once that spec is approved, so the next real build is the demo (open question 2). Before/after shots go on Design Votes via `ui_shots.py`.

6. **The README: `GOAL_AGENT.md`** (deliverable 3). It answers the three questions the course asks:
   - what the agent built (the 0.1.4 features, linked to their commits);
   - why it selected each one, quoted from the blackboard's scores;
   - every manual change made before accepting the code, from Process 9's Fixes list. An orchestrator fix counts as manual.
   It also says how the loop works and what it cost (`agent-runs.csv`). It's submitted as a demo link with the source and the playable build (deliverables 1 and 2).

## Order

1. `scan()`, `gaps()` and `priority_score()` with their fixtures and unit tests. It's cheap and needs no Godot.
2. The orchestrator runs `goal_agent.py --plan` on 0.1.4 (gaps and scores only, no writes), and the designer reads the order.
3. The loop, run first with `--dry-run` (prints briefs and commands, spends nothing), then for real on one goal only.
4. The full 0.1.4 run, then `GOAL_AGENT.md`.

## Done when

- `gaps()` marks 0.1.3's changes as done and 0.1.4's as missing, with evidence for each.
- The `priority_score()` order for 0.1.4 respects the node contract (handoff before scenes), and the blackboard gives each goal's factors.
- The loop builds at least one 0.1.4 goal to green with a checkpoint commit and re-scans, or stops with a clear question when it can't. The built feature runs in the game (deliverable 2).
- The blackboard and `GOAL_AGENT.md` show the whole run, including its cost and the manual changes.
